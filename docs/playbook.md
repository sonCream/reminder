# PWA 알림 앱 플레이북

같은 환경(Next.js + PWA + 웹 푸시 + Docker + AWS)에서 다른 앱을 만들 때
처음부터 다시 헤매지 않기 위한 문서다.

무엇을 만들었는지가 아니라 **무엇에 걸렸고 왜 그렇게 풀었는지**를 남긴다.

---

## 1. 이 구조가 맞는 앱 / 아닌 앱

**맞는 앱**

- 정해진 시각에 사용자에게 **먼저 말을 거는** 앱 (리마인더, 예약 알림, 정기 결제 안내)
- 사용자가 앱을 열지 않아도 가치가 발생하는 앱
- 스토어 심사 없이 빠르게 배포하고 자주 고쳐야 하는 앱

**아닌 앱**

- 알림음이나 진동 패턴이 제품의 핵심인 앱 → 웹에서 지정 불가
- 정시 도달이 반드시 보장돼야 하는 앱(기상 알람) → 웹 푸시는 FCM/APNs 경유라 지연 가능
- 오프라인에서 대부분의 일을 하는 앱

---

## 2. 이 프로젝트의 출발점이 된 사실

> **PWA는 정해진 시각에 스스로 깨어날 수 없다.**

웹 표준에 그 수단이 없다(Notification Triggers 는 시도됐다가 폐기됐다).
네이티브 앱이라면 OS 에 알림을 예약하고 끝이지만, PWA 는 그럴 수 없다.

그래서 구조가 이렇게 정해진다.

```
[네이티브]  앱이 OS 에 예약  →  OS 가 알림                    (서버 불필요)
[PWA]      서버가 시각 관리 → 웹 푸시 → 서비스 워커 → 알림   (서버 필수)
```

**서버와 스케줄러는 선택이 아니라 전제다.** 이걸 모르고 시작하면
"로컬 DB 만으로 만들겠다" 같은 계획을 세웠다가 중간에 전부 뒤집게 된다.

---

## 3. 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | Next.js (App Router) | 화면과 API 를 한 프로젝트에서 |
| DB | PostgreSQL + Prisma | `timestamptz` 로 시간대를 DB 가 다룬다 |
| 알림 | web-push (VAPID) | 무료, 심사 없음, 서류 없음 |
| 스케줄러 | node-cron **별도 프로세스** | 서버리스 크론은 분 단위에 제약이 많다 |
| 개발 | Docker Compose (db + app + worker) | |
| 운영 | EC2 + Caddy + RDS | Caddy 가 HTTPS 를 자동 발급·갱신 |

**⚠️ Prisma 는 6 을 쓴다.** 7 부터 `url = env("DATABASE_URL")` 이 폐지되고
별도 설정 파일 + 드라이버 어댑터를 요구한다. 검색해서 나오는 예제 대부분이 6 기준이다.

**⚠️ 스케줄러를 서버리스로 두지 않는다.** 분 단위 실행이 필요한데
Vercel 무료 플랜의 크론은 하루 1회다. 상시 실행 프로세스가 필요하다.

## 4. 재사용할 수 있는 세 가지 구조

### 4-1. 중복 없이 누락 없이 도는 스케줄러

발송 예약을 별도 테이블로 두고, **스키마에 중복 차단 장치를 박는다.**

```prisma
model Notification {
  reminderId   Int
  occurrenceAt DateTime   // 반복의 몇 번째 회차인가
  kind         String     // main | lead | snooze
  channel      String     // push | email | console
  scheduledAt  DateTime
  status       String     @default("pending")

  @@unique([reminderId, occurrenceAt, kind, channel])  // ★ 로직에 버그가 있어도 DB 가 막는다
  @@index([status, scheduledAt])
}
```

워커는 이렇게 돈다.

```ts
// ① "지금" 이 아니라 "예정 시각이 지났는데 아직 안 보낸 것 전부" 를 찾는다.
//    → 서버가 죽어 있던 동안 밀린 알림이 재가동 시 자동으로 나간다.
const due = await prisma.notification.findMany({
  where: { status: 'pending', scheduledAt: { lte: new Date() } },
  orderBy: { scheduledAt: 'asc' },
  take: 50,
})

for (const n of due) {
  // ② 조건부 갱신. 갱신된 행이 0이면 다른 워커가 이미 집어간 것이다.
  const { count } = await prisma.notification.updateMany({
    where: { id: n.id, status: 'pending' },
    data: { status: 'sending', attempts: { increment: 1 } },
  })
  if (count !== 1) continue

  // ③ 실패하면 pending 으로 되돌려 다음 틱에 재시도, 3회 넘으면 failed
}
```

**이 세 줄이 핵심이다.** ①이 누락을, ②가 중복을 막는다.

### 4-2. 발송 채널 추상화

```
Notifier (인터페이스)
├── ConsoleNotifier   개발 초기. VAPID·SMTP 없이도 스케줄러를 검증할 수 있다
├── EmailNotifier     보조 수단
├── PushNotifier      본 수단
└── (나중에) AlimTalkNotifier / SmsNotifier
```

**이걸 처음부터 인터페이스로 두면 외부 서비스 승인을 기다리며 개발이 멈추지 않는다.**
카카오 알림톡처럼 사업자 서류·템플릿 심사가 필요한 채널은 개통에만 수일이 걸린다.

`.env` 의 `NOTIFIER_CHANNELS=console,push` 로 켜고 끈다.

### 4-3. 익명 키 계정

이메일도 비밀번호도 받지 않는다. 앱이 처음 열릴 때 서버가 무작위 키를 발급하고
기기가 보관한다. **서버는 그 계정이 누구인지 모른다.**

```
앱 열기 → 키가 있으면 세션으로 교환 → 쿠키
          키가 없으면 계정 생성 + 키 발급
```

| | 이메일 로그인 | 익명 키 |
|---|---|---|
| 수집하는 개인정보 | 이메일 | **없음** |
| 로그인 단계 | 있음 | **없음** |
| 다기기 | 자동 | 키를 옮겨야 함 |
| 복구 | 가능 | **불가 — 키를 잃으면 끝** |
| 발송 인프라 | SMTP 필요 | 불필요 |

**외부 공개를 염두에 둔다면 익명 키가 부담이 훨씬 적다.**
다만 키 백업 UI(QR + 문자열)와 재발급이 필수다.

⚠️ **키는 해시로만 저장한다.** DB 를 볼 수 있어도 남의 계정이 되지 못하게.

## 5. PWA 의 경계선 — 웹이 못 하는 것

**이 표가 이 프로젝트에서 가장 값진 지식이다.** 기획 단계에서 먼저 봐야 한다.

| 기능 | iOS | Android | 비고 |
|---|---|---|---|
| 웹 푸시 알림 | ✅ 16.4+ | ✅ | iOS 는 **홈 화면 추가 필수** |
| 아이콘 숫자 배지 | ✅ 16.4+ | ❌ | Android 는 런처가 알림 개수를 점/숫자로 표시 |
| 알림 버튼(완료·나중에) | ❌ | ✅ | iOS 는 누르면 앱이 열리는 동작만 |
| **알림음 지정** | ❌ | ❌ | **웹에서 불가. 기기 기본음만** |
| **화면 위 팝업 여부** | 기본 O | ⚠️ 사용자 설정 | Android 는 채널 중요도를 사용자만 바꿀 수 있다 |
| 정해진 시각 자체 기상 | ❌ | ❌ | 서버 푸시가 유일한 수단 |
| 정시 도달 보장 | ❌ | ❌ | FCM/APNs 경유 |

**"껍데기만 씌우면 해결된다"는 기대는 대체로 어긋난다.**
Android TWA 는 내부적으로 Chrome 이 돌아서 위 제약을 그대로 물려받는다.
알림음과 숫자 배지를 얻으려면 Capacitor 등으로 **알림 계층을 네이티브로 다시 짜야** 한다.

## 6. 함정 모음

### 6-1. 개발 환경

**프로젝트 경로에 `&` 가 있으면 npm 이 깨진다**

```
D:\R&D\project3  →  npx next  실행 시 D:\next\... 를 찾는다
```

`npm run dev`, `npx prisma` 등 거의 모든 명령이 실패한다. 경로를 바꾸는 것 말고 답이 없다.

**Windows 바인드 마운트에서는 파일 변경이 컨테이너로 전달되지 않는다**

코드를 저장해도 화면이 그대로다. `docker-compose.yml` 에 폴링을 켠다.

```yaml
WATCHPACK_POLLING: "true"
CHOKIDAR_USEPOLLING: "true"
```

그래도 **새로 만든 파일이나 디렉터리는 놓칠 때가 있다.** 그때는 컨테이너를 재시작한다.

**컨테이너의 `node_modules` 는 별도 볼륨이다**

Windows 에서 바인드 마운트로 두면 파일이 수만 개라 매우 느려서 분리했는데,
그래서 **호스트의 `npm install` 이 컨테이너에 반영되지 않는다.**
`Module not found` 가 나면 이것이다. 두 번 설치해야 한다.

```bash
npm install <패키지>                    # 호스트 (타입 검사·에디터)
docker compose exec app npm install     # 컨테이너 (실행)
```

Prisma 스키마를 바꿨을 때도 `docker compose exec app npx prisma generate` 를 잊지 않는다.

**`prisma migrate dev` 는 비대화형 환경에서 파괴적 변경을 못 한다**

테이블을 지우는 마이그레이션은 확인을 요구하는데 스크립트에서는 답할 수 없다.
`prisma/migrations/<타임스탬프>_<이름>/migration.sql` 을 직접 쓰고 `migrate deploy` 로 적용한다.
데이터 이관 SQL 을 끼워 넣어야 할 때도 이 방법을 쓴다.

### 6-2. Next.js

**`NEXT_PUBLIC_*` 는 빌드 시점에 코드로 박힌다**

도커 빌드 중에는 `.dockerignore` 때문에 `.env` 가 없다.
그래서 값이 `undefined` 로 굳는다. **개발에서는 되는데 운영에서만 깨진다.**

→ 빌드 인자로 넘기지 말고 **실행 시점에 API 로 내려준다.**
같은 이미지를 어디서나 쓸 수 있고 값을 바꿔도 재빌드가 필요 없다.

**미들웨어는 Edge 런타임이라 Prisma 를 못 쓴다**

세션 검증처럼 DB 조회가 필요한 일은 미들웨어에서 할 수 없다.
쿠키 존재 여부만 보고, 실제 검증은 API 라우트에서 한다.

```ts
// 미들웨어에서 lib/auth.ts 를 import 하면 Prisma 가 딸려온다.
// 상수만 담은 별도 파일로 분리한다.
export const SESSION_COOKIE = 'app_session'
```

**클라이언트에서 시각을 계산하면 하이드레이션이 어긋난다**

서버와 브라우저의 "지금" 이 다르다.
`now` 를 `null` 로 시작해 마운트 후 채우고, 그전에는 로딩 상태를 그린다.

### 6-3. 서비스 워커 · 알림

**서비스 워커는 보안 컨텍스트에서만 동작한다**

| 주소 | 결과 |
|---|---|
| `http://localhost` | ✅ 예외적으로 허용 |
| `http://192.168.x.x` | ❌ **폰에서 테스트 불가** |

폰 테스트는 배포된 HTTPS 주소나 Cloudflare Tunnel 로 해야 한다.
이걸 모르고 마지막 주에 폰을 꺼내면 일정이 무너진다.

**알림 `tag` 를 재사용하면 팝업이 생략된다**

같은 `tag` 로 알림을 보내면 Android 는 "기존 알림 교체" 로 처리하고
**화면 위 팝업(heads-up)을 띄우지 않는다.** 목록에는 들어오는데 안 뜬다.
`requireInteraction: true` 로 이전 알림이 남아 있으면 매번 교체가 된다.

→ **회차마다 다른 tag** 를 쓴다. 서버의 발송 건 id 가 적당하다
(회차마다 다르고, 재시도할 때는 같아 중복 방지는 유지된다).

**`0` 은 falsy 다**

```js
if (!data.reminderId) return   // reminderId 가 0 이면 여기서 조용히 빠져나간다
```

테스트 알림에 `reminderId: 0` 을 넣었더니 버튼이 보이는데 눌러도 아무 일이 없었다.
서비스 워커는 화면이 없어서 이런 실수가 드러나지 않는다.

**Android 팝업은 앱이 못 켠다**

알림 채널 중요도는 사용자만 바꿀 수 있다. 웹 API 에 그 수단이 없다.

⚠️ **설정 경로를 문서에 못박지 말 것.** 제조사·OS 버전마다 다르고 금방 낡는다.
대신 **기종을 타지 않는 방법**을 안내한다.

```
알림을 상단바에서 길게 누르기 → 톱니바퀴(⚙) → 긴급 / 알림 팝업 켜기
```

문구도 하나로 정하지 않고 `팝업 · 긴급 · 소리 및 팝업` 중 보이는 것을 고르라고 한다.

**iOS 는 7일 이상 방문 없는 사이트의 저장소를 비운다**

계정 키를 `localStorage` 에 둔다면 **홈 화면 추가는 권장이 아니라 필수 조건**이 된다.
홈 화면에 추가한 앱은 예외다.

**Android 는 홈 화면에서 앱을 지워도 사이트 데이터가 남는다**

푸시 구독과 진행 상태가 그대로라 **다시 설치해도 이미 끝난 것처럼 보인다.**
온보딩에 초기화 수단을 넣어둔다.

### 6-4. 시간 계산

**DB 는 UTC, 표시는 현지, 요일 판정은 현지 기준**

```
07:00 KST = 전날 22:00 UTC
```

UTC 요일을 그대로 쓰면 "평일만" 반복이 하루씩 어긋난다.
한국은 서머타임이 없어 고정 +9 로 계산해도 되지만,
**요일과 날짜 판정만은 현지 기준으로 옮겨서** 해야 한다.

**말일과 윤년**

1월 31일 + 1개월 = 2월 28일(윤년이면 29일), 2월 29일 + 1년 = 2월 28일.
클램핑 처리가 필요하다.

**밀린 회차를 전부 보내면 안 된다**

한 달 자리를 비우면 "약 먹기" 알림이 30개 쌓인다.
지나간 회차는 건너뛰고 **앞으로 올 첫 회차 하나만** 잡는다.

**이런 계산은 눈으로 못 잡는다.** 검증 스크립트를 반드시 만든다.

```bash
npm run check:repeat   # 말일·윤년·주말 건너뛰기·밀린 회차 10건
```

### 6-5. React

**이벤트 핸들러가 state 를 읽으면 배치 때문에 옛 값을 본다**

스와이프 제스처에서 이동량을 state 로 읽었더니,
**천천히 밀면 되고 빠르게 밀면 안 되는** 버그가 생겼다.
프레임마다 리렌더링될 때만 우연히 동작한 것이다.

→ 판정에 쓰는 값은 **ref 로도 들고 있는다.**

**`localStorage` 변경은 다른 컴포넌트에 전파되지 않는다**

설정 화면에서 값을 바꿔도 이미 떠 있는 화면은 예전 값을 들고 있다.
저장 시 구독자에게 알리는 얇은 pub/sub 을 둔다.

**다른 화면을 다녀와야 완료되는 단계가 있으면 `visibilitychange` 로 재확인한다**

홈 화면에 추가하거나 시스템 설정을 만지고 돌아왔을 때
화면이 그대로면 "했는데 왜 반영이 안 되지?" 가 된다.

### 6-6. 보안

**id 만 알면 남의 데이터를 고칠 수 있게 두지 않는다**

인증을 붙였다고 끝이 아니다. 모든 조작 함수에 소유권 검사를 넣는다.

```ts
async function requireOwned(id: number, userId: string) {
  const row = await prisma.reminder.findFirst({ where: { id, userId } })
  if (!row) throw new NotFoundError()   // 403 이 아니라 404
  return row
}
```

**403 대신 404 를 돌려준다.** 그 id 가 존재한다는 사실조차 알릴 필요가 없다.

**메일을 못 보내는 상태에서 로그인 링크를 응답에 실으면 안 된다**

개발 편의로 넣은 코드가 운영에 남으면 **누구나 남의 주소로 로그인**할 수 있다.
`NODE_ENV === 'production'` 이면 차라리 503 을 돌려준다.

**토큰과 키는 해시로 저장한다**

## 7. AWS 배포에서 걸리는 것

| 항목 | 주의 |
|---|---|
| **리전** | 서울(ap-northeast-2). 다른 리전에 만들면 목록에 안 보이는데 요금은 나간다 |
| **EC2 크기** | ⚠️ t3.micro(1GB)는 `next build` 도중 죽는다. **t3.small 이상 + 스왑** |
| **탄력적 IP** | 실행 중인 인스턴스에 연결돼 있으면 무료, 놀리면 과금 |
| **RDS 퍼블릭 액세스** | **끈다.** 켜두면 몇 시간 내 스캐닝 대상 |
| **RDS 보안 그룹** | IP 가 아니라 **EC2 의 보안 그룹 ID** 로 지정 |
| **초기 DB 이름** | ⚠️ `추가 구성` 안에 접혀 있다. 빠뜨리면 `database does not exist` |
| **엔진 선택** | 메뉴가 `Aurora and RDS` 라 Aurora 를 고르기 쉽다. **Aurora 는 프리티어 아님** |
| **마이그레이션** | 운영은 `migrate deploy`. `migrate dev` 는 데이터를 지울 수 있다 |
| **도메인** | Route 53 등록비는 **크레딧으로 결제되지 않는다.** 밖에서 사는 게 싸다 |
| **인증서** | ACM 은 EC2 에 직접 못 붙인다. **Caddy + Let's Encrypt** 가 맞다 |
| **Free plan** | ⚠️ **6개월 뒤 계정이 자동으로 닫힌다.** 복구 기한 90일 |

**DNS 는 EC2 의 고정 IP 가 나와야 신청할 수 있고, 사내 결재가 걸리면 며칠 간다.**
가장 먼저 착수할 것.

⚠️ **사내 전용 DNS 는 안 된다.** Let's Encrypt 가 외부에서 도메인 소유를 확인하지 못해
인증서 발급이 실패한다. 신청할 때 "외부 공개 DNS 등록" 을 명시한다.

## 8. 처음부터 다시 만든다면 이 순서

```
1일차   기술 검증 — 가장 위험한 것 하나만 골라 먼저 확인
        (이 프로젝트에서는 "웹 푸시가 실제로 오는가")

2~3일   로컬 환경 — Docker + DB + 스키마 + 스케줄러
        발송은 ConsoleNotifier 로. 외부 서비스 없이 여기까지 검증한다

4~5일   화면 — 알림 없이도 완결되는 상태까지
        ★ 여기까지가 안전선. 이후가 다 막혀도 보여줄 게 남는다

6~7일   배포 — 도메인·HTTPS·서버
        ★ 폰에서 처음 써보는 시점. 미룰수록 위험하다

8~     푸시 → 알림 관련 기능 → 인증 → 온보딩
```

**배포를 늦추지 않는다.** 폰에서 못 써보는 상태로 만드는 기능은 전부 추측이다.
이 프로젝트에서 실제로 나온 문제(팝업, 배지, 저장소 삭제, 재설치)는
**전부 실기기에서만 드러났다.**

## 10. 마지막으로

이 프로젝트에서 시간을 가장 많이 잡아먹은 것은 **코드가 아니었다.**

- 경로의 `&` 하나
- 컨테이너 안팎의 `node_modules` 불일치
- 빌드 시점에 박히는 환경변수
- 기종마다 다른 알림 설정 메뉴

**"개발에서는 되는데 운영에서만 안 되는" 유형이 대부분이었다.**
그래서 배포를 일찍 하고, 실기기로 자주 확인하는 것이
어떤 설계 결정보다 일정에 큰 영향을 준다.
